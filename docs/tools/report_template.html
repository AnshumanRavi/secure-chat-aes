In one paragraph. SecureChat lets two or more laptops on the same network chat through a familiar WhatsApp-style app. Each connection starts with an RSA-2048 key exchange that produces a fresh AES-256 key; from then on every packet is encrypted and authenticated with AES-256-GCM, carries a sequence number and timestamp against replay, and is checked before use. Passwords are stored as salted PBKDF2 hashes, and an optional end-to-end mode keeps even the server from reading one-to-one chats. Built-in attack tools prove that sniffing, tampering, replaying and password guessing all fail, and benchmarks show the whole protection adds well under a millisecond per message.

1Project Overview

On a shared network such as a college Wi-Fi, anyone between two computers can capture, change or resend the data they exchange. A chat program that sends plain text exposes every message and every password. The aim of this project was to build a chat application that stays private and trustworthy even on such a network — and to measure what that protection costs.

Project goal: develop a secure client–server chat application using AES encryption.

3How It Works

A central server relays messages between the apps. The network in between is assumed to be hostile: everything that crosses it is encrypted and authenticated.

Architecture

Figure 3.1 — The parts of the system and where the attacker sits.

Every client has its own encrypted connection to the server. When User A sends a message to User B, the server decrypts it with A's session key, checks it, and re-encrypts it with B's key — so the bytes on the two connections look completely different. In end-to-end mode the message is additionally sealed with a key only A and B know, and the server simply passes it on.

The secure handshake

Before any chatting, client and server agree on a fresh secret key over the open network:

Figure 3.2 — The handshake. Green arrows are already encrypted.

RSA is used only once, to carry a small random secret; fast AES protects everything after that. Because the server adds a new salt every time, every connection ends up with a different key — even a complete recording of an old session is useless later.

4Cryptography Used

Each building block was chosen for a specific job. Here is what each one does, in plain words, and why it was chosen.

AES-256-GCM every message

What: the AES block cipher with a 256-bit key in Galois/Counter Mode — encryption plus a 128-bit authentication tag in one step (an "AEAD" cipher).

Why: it gives secrecy and tamper detection together, needs no padding, is hardware-accelerated, and is the cipher TLS 1.3 uses. A fresh random 96-bit nonce is used for every packet, because reusing one would break GCM.

RSA-2048 with OAEP once per connection

What: public-key encryption — anyone can lock data with the server's public key, only the server can unlock it.

Why: it solves the "how do we agree on a key over an open network" problem. OAEP padding makes it randomised and secure against chosen-ciphertext attacks; 2048 bits gives ≈112-bit security.

HKDF-SHA256 key derivation

What: turns a random secret (plus the server's salt) into a proper AES key.

Why: both sides contribute randomness, every session gets a different key, and separate keys can be derived for separate jobs instead of reusing one key everywhere.

PBKDF2-HMAC-SHA256 passwords

What: a deliberately slow, salted password hash — 200,000 rounds of HMAC-SHA256.

Why: the server never stores passwords. If its database were stolen, each password guess would cost an attacker as much as a real login: only about 74 guesses per second per CPU core.

ECDH on P-256 end-to-end mode

What: elliptic-curve Diffie–Hellman — two users combine their own private key with the other's public key and both arrive at the same secret.

Why: the shared key is never sent anywhere, so the server can relay messages but never read them. A 60-digit security code lets users check nobody swapped a key.

SHA-256 and HMAC integrity

What: cryptographic fingerprints of data.

Why: used to identify the server's key (its fingerprint), to verify whole files after transfer, and to hide contact names in the local history file.

Why AES-GCM and not another AES mode?

ModeHow it worksDetects tampering?Verdict
ECBEach 16-byte block encrypted separately — identical blocks give identical ciphertext, so patterns show through (the famous "ECB penguin")NoInsecure
CBCBlocks chained together with a random IV; needs padding and a separate HMAC, and mistakes lead to padding-oracle attacksOnly with an extra HMACAcceptable, slower
CTRTurns AES into a stream cipher; fast, but flipping a ciphertext bit flips the same plaintext bit unnoticedNoNot enough alone
GCMCTR encryption plus an authentication tag over the ciphertext and context Yes, built inChosen ✓
Measured on the test laptop for 1 MB of data: GCM encrypts at 1,015 MB/s against 388 MB/s for CBC + HMAC (2.6× faster), and adds 28 bytes per message instead of 64. For very small messages CBC + HMAC is about 20 µs faster in PyCryptodome — a difference no user can notice.

7Running on Two Laptops

The project is designed to run across two laptops on the same Wi-Fi network — no command line needed.

  1. Install Python (3.11 or newer) on both laptops and copy the project folder to each.
  2. Laptop 1: double-click run_server.bat. The first run installs everything automatically and asks for a passphrase that protects the server's private key. The window then shows "Clients on other PCs should connect to: 192.168.x.x:5555" and the key fingerprint.
  3. Laptop 1, once: right-click allow_firewall.bat → Run as administrator, so Windows Firewall lets the other laptop in.
  4. Laptop 2: double-click run_client.bat, press Find server on LAN (or type the address), create an account and confirm the fingerprint matches the server window.
  5. Laptop 1: open run_client.bat too, create a second account — and chat.
College Wi-Fi blocking it? Many campus networks stop laptops from talking to each other ("client isolation"). Turning on a phone hotspot and connecting both laptops to it solves this — the chat traffic stays between the laptops and uses no mobile data. Both laptops' clocks should also be in sync, because packets more than 60 seconds old are rejected as possible replays.

For a laptop without Python, the project can be packaged into a standalone SecureChat.exe (with PyInstaller). A step-by-step deployment and troubleshooting guide is included in the repository (docs/DEPLOYMENT.md).

Security review

A final code review searched specifically for key or nonce reuse, information leaking through errors or logs, thread-safety problems and missing input checks. It found and fixed, among others: passwords in Hindi or Chinese crashing registration; a file name trick that could disguise a .exe as a .jpg; file transfers left hanging when a sender disconnected; and unbounded server memory use under attack. Each fix has its own test.

9Limitations and Future Work

Current limitations

  • No forward secrecy. The session secret is protected by the server's long-term RSA key. If that key and its passphrase were ever stolen, recorded past sessions could be decrypted. Real messengers avoid this with fresh Diffie–Hellman keys for every session.
  • End-to-end mode covers one-to-one text chats. Group chats and files are encrypted on the network, but the server can read them.
  • The server knows who talks to whom (metadata), though not what end-to-end messages say.
  • Trust on first use: a user who skips comparing the fingerprint on the very first connection could be fooled once.
  • Scale: one Python server process handles about 1,300 messages per second — plenty for a class, not for millions of users.

Future work

  • Use ephemeral elliptic-curve Diffie–Hellman (X25519) for forward secrecy, and the Signal protocol's Double Ratchet for end-to-end chats, as WhatsApp does.
  • End-to-end encryption for groups and files.
  • Argon2id password hashing, and a server certificate instead of trust on first use.
  • A multi-process server, a mobile app, and disappearing messages.

10Conclusion

SecureChat meets every task of the project.

Two laptops chat through a polished, WhatsApp-style application while every packet on the network is encrypted and authenticated with AES-256-GCM under a fresh key agreed with RSA-2048-OAEP and HKDF. Received packets are decrypted only after their authentication tag is verified, so modified, replayed and forged packets are rejected. Unauthorized access is prevented at every level: hashed passwords with lockout, server fingerprint checking against man-in-the-middle attacks, encrypted storage, and an optional end-to-end mode that even the server cannot read. Live demonstrations show eavesdropping, tampering, replay and password guessing all failing.

The performance evaluation shows the protection is effectively free for users: AES-256-GCM runs at about 1 GB/s, the handshake costs 2 ms once per connection, and the complete secure protocol adds about two-thirds of a millisecond to each message.

The most important lesson of the project is that encryption alone is not enough: it is authenticated encryption, careful key and nonce handling, and protection against replay and impersonation that together make communication secure.
